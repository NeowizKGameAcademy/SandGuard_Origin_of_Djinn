# 인터페이스 구조 개선 작업 기록

기준: 2026-09-08 구조 검토와 사용자의 작업 진행 요청.

## 반영한 내용

| 부분 | 바뀐 내용 | 이유 |
|---|---|---|
| 공격 대상 선택 | 대상과 접근 위치, 길 정보 번호를 TargetSelection으로 함께 전달 | 길을 막은 시설까지 갈 수 있는 위치가 중간에 사라지지 않게 함 |
| 지정 건설 슬롯 | 레벨 데이터, 편집기 배치, 저장·불러오기, 조회와 점유 관리 추가 | 화면과 건설 코드가 같은 슬롯 정보를 사용 |
| 점프·대시 | 입력 알림과 화면용 상태 조회 추가 | 버튼 입력과 실제 사용 가능 여부를 구분 |
| 시설 강화 | 강화 비용 조회와 강화 요청 추가 | 수리·철거와 같이 비용을 쓰는 시설 관리 기능으로 모음 |
| 시설 화면 정보 | BuildResult에 FacilityViewData만 전달하고 IFacilityQuery 추가 | 화면이 시설의 체력이나 제거 기능을 직접 호출하지 못하게 함 |
| 대상 선택 규칙 | 사용처 없는 ITargetPolicy 제거, PriorityTargetPolicy 클래스 유지 | 하나뿐인 계산 코드에 별도 인터페이스를 두지 않음 |
| 반환값 설명 | 공격 시작, 조회 실패, 같은 일시정지 요청의 결과를 명시 | 구현하는 사람마다 의미가 달라지는 것을 방지 |

기존 인터페이스와 메서드의 쉬운 한글 주석을 유지했고, 새 인터페이스에도 같은 방식으로 설명을 달았다. 인터페이스는 37개에서 39개가 됐다. 필요한 조회 역할 세 개를 추가하고 중복 역할 하나를 제거했다. 인터페이스 수를 줄이는 것 자체를 목표로 삼지는 않았다.

## 지정 슬롯 사용 방법

1. 레벨 편집기의 마커 화면에서 **건설 슬롯 클릭 배치**를 누르고 바닥을 클릭한다.
2. 슬롯을 선택해 **바닥 ID**와 **허용 시설 ID**를 입력한다. 허용 시설 목록이 비었으면 아무 시설도 지을 수 없다.
3. 같은 바닥의 자유 배치와 슬롯은 같은 바닥 ID를 쓴다. 위아래 층에는 서로 다른 ID를 쓴다.
4. 슬롯을 복제했다면 **이 슬롯에 새 ID 부여**로 중복 ID를 바꾼다.
5. 레벨 검사 후 저장한다. 새 저장은 버전 2이며 기존 버전 1도 불러올 수 있다.

슬롯의 ID·위치·회전·자리 크기·허용 시설·건설 허용 여부를 저장한다. 비활성 슬롯은 저장 시 건설 불가로 기록한다. 플레이 중 어느 시설이 차지했는지는 레벨 배치 파일에 저장하지 않는다.

BuildSlotRegistry는 LevelRoot에서 현재 슬롯을 읽는다. GetSnapshot은 복사한 목록을 주며 TryGetSlot은 호출 시점의 위치를 준다. 잘못된 설정이나 중복 ID는 건설 가능한 슬롯으로 내보내지 않는다. 부모 레벨에서 자식 레벨의 슬롯을 가져오지 않는다.

건설 코드에서는 다음처럼 기존 단계 검사에 슬롯 검사를 추가할 수 있다.

```csharp
var slots = new BuildSlotRegistry(levelRoot);
var validator = new CompositePlacementValidator(new IPlacementRule[]
{
    new PlacementPhaseRule(gameState),
    new SlotPlacementRule(slots)
    // 실제 건설 서비스에서 공간 충돌, 바닥, 해금, 비용 검사도 연결한다.
});
```

위 코드는 연결 예시다. 검사 두 개만으로 완전한 건설 조건을 확인한 것은 아니다. 슬롯이 비어 있어도 자유 배치 시설이나 캐릭터와 실제로 겹칠 수 있다.

실제 건설 서비스는 최종 실행 시 슬롯을 다시 조회해야 한다. TryOccupy로 한 시설의 자리를 잡고, 생성 실패나 철거 시 같은 시설 ID로 Release한다. 이 기능은 Unity 주 스레드에서 사용한다. 마나 예약·시설 생성·자리 확보를 끝내기 전에는 외부 알림이나 비동기 대기를 끼워 넣지 않는다. 실패 시 모두 되돌리는 일은 건설 서비스가 맡는다. 레벨이나 게임을 새로 시작할 때는 새 등록소를 만든다.

## 바뀐 API를 사용할 때

- ITargetSelector.CurrentTarget은 CurrentSelection으로 바뀌었다. SelectTarget도 TargetSelection을 반환한다. 대상이 없으면 기본값이다. 원래 진격 목적지는 AI가 따로 기억한다. HasCurrentApproach로 길 정보 번호를 확인하고, 위치의 유효성·현재 거리·시야는 이동·공격 시 다시 검사한다.
- BuildResult.Built는 IFacility 대신 FacilityViewData를 받는다. 성공 결과의 Facility는 표시 값이고 실패 시 null이다. 시설 메뉴는 IFacilityQuery로 다시 조회하고 IFacilityMaintenance에 행동을 요청한다.
- IFacility는 건설·관리 코드가 사용하는 내부 기능 묶음으로 유지했다. 강화 단계 조회도 추가했다. 화면으로 직접 전달하지 않는다.
- IFacilityMaintenance의 GetUpgradeQuote/TryUpgrade가 다음 한 단계 강화를 맡는다. 최대 단계에서 성공 견적을 만들 수 없다. 실제 서비스는 실행할 때 현재 단계와 마나 등을 다시 확인해야 한다.
- IPlayerInput에 JumpPressed/DashPressed를 추가했다. IPlayerMobilityReader는 접지 상태, 남은 추가 점프, 대시 비용과 남은 대기 시간, 사용 가능 여부를 제공한다. 키 배정과 실제 이동 처리는 아직 연결하지 않았다.
- TryAttack의 true는 공격 동작을 시작했다는 뜻이며 명중 보장은 아니다. TryGet 실패는 null 또는 기본값이다. TrySetPaused는 이미 원하는 상태여도 true이며 실제 변화가 있을 때만 알린다.

변경 당시 ITargetSelector, IFacility, IFacilityMaintenance, IPlayerInput 등의 실제 구현체나 해당 건설 결과를 소비하는 게임 코드는 없었다. 따라서 기존 게임 구현체를 임시로 비워 두는 수정은 필요하지 않았다.

## 이번 작업의 범위

실제 코드로 연결한 부분은 슬롯 데이터·조회·점유 검사와 레벨 편집·저장이다. 목표 선택 결과, 시설 강화, 시설 표시 조회, 점프·대시는 인터페이스와 전달 데이터까지 준비했다.

FacilityBuilder, 시설 강화 서비스, PlayerMotor, 입력 연결, 실제 HUD, 적 AI는 아직 없다. 층별 위험 표시, 보스의 시설 정지 효과, 소환수 관리 등은 해당 게임 동작을 구현할 때 필요한 범위로 연결한다.

준비 단계의 지정 슬롯, 전투 단계의 자유 배치 허용, 포인트를 쓰는 선택형 성장, 코어 도착 즉시 흡수 및 공격 파괴 전환 준비는 그대로 유지했다. 비용·개수·강화 한도 같은 조정 값은 고정하지 않았다.

## 검증

Unity EditMode 테스트 결과는 아래 기록에 남긴다.

- 결과: **73개 모두 통과** (기존 50개 + 신규 23개, 실패·건너뜀 0개)
- 결과 파일: Logs/InterfaceStructure/editmode-results-final.xml
- Unity 로그: Logs/InterfaceStructure/unity-editmode-final.log
- 기존 50개 테스트와 신규 23개 테스트를 함께 실행했다.
- 새 테스트는 슬롯 저장·복원·되돌리기, 잘못된 저장 데이터의 기존 레벨 보호, 소유 시설만 자리 해제, 조회 결과 복사, 자유 배치 유지, 접근 위치 전달, 화면 데이터의 기능 노출 방지를 확인한다.

테스트 통과는 아직 없는 게임 서비스의 플레이 동작까지 완성됐다는 뜻은 아니다.
