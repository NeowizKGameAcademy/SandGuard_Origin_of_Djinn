# DESERT TOWER 공통 전투 기반 시스템 설계

버전: 0.1
작성일: 2026-09-06
기준 문서: Desert_Tower_상세_게임기획서_v0.2 (11.1 "공통 체력·피해·사망 처리와 진영 구분")
문서 성격: 구현 전 설계 기준. 코드 없음. 기획서 규칙과 충돌하면 기획서를 우선하고 이 문서를 고친다.

## 0. 이 시스템이 존재하는 이유

기획서에는 체력을 갖고 피해를 받는 것이 일곱 종류 있다. 플레이어, 일반 근접 적, 강한 근접 적, 하수인, 벽, 공격 타워, 소환 타워, 그리고 코어다. 이들은 TPS 코어·타워 디펜스 코어·EnemyAI 세 갈래에 흩어져 있지만, "맞으면 체력이 줄고, 0이 되면 무언가 일어나며, 그 사실을 다른 시스템이 알아야 한다"는 규칙은 전부 같다.

이 규칙을 각 시스템이 따로 구현하면 기획서 13.1의 검증 항목 세 가지가 바로 깨진다. "모든 처치 주체가 동일하게 경험치·마나를 지급하는가", "타워 파괴 시 소속 하수인과 관련 상태가 정리되는가", "재시작 시 이전 시설·적·성장 상태가 남지 않는가"는 모두 **하나의 공통 경로**로 피해와 사망을 처리해야만 보장된다.

공통 전투 기반은 그 하나의 경로다. 세 코어 시스템 아래에 깔리고, 세 시스템은 이 기반을 통해서만 서로의 체력을 건드린다.

## 1. 책임 경계

### 1.1 소유하는 것

- 전투 개체의 등록과 식별 (누가 전장에 있는가)
- 진영과 적대 관계 판정
- 체력의 저장, 감소, 회복, 상한 처리
- 피해 요청의 접수·검증·적용
- 사망·파괴·소멸·다운의 생명주기와 그 순서 보장
- 사망 사실을 **정확히 한 번** 외부에 알리는 것
- "이 개체가 지금 유효한 공격 대상인가"라는 질의
- 거리·시야 확인에 쓰는 공통 기준점(피격 지점, 장애물 판정 규칙)
- 재시작 시 모든 전투 개체의 일괄 정리

### 1.2 소유하지 않는 것

| 하지 않는 일 | 담당 시스템 | 이유 |
|---|---|---|
| 누구를 공격할지 고르기 | EnemyAI, 공격 타워, 하수인 | 판단 규칙이 종류마다 다름 (기획서 4.3, 5.4, 5.5) |
| 사거리·시야를 만족하는지 확인 후 공격 개시 | 각 공격 주체 | 기반은 확인 도구만 제공, 판단은 공격자 몫 (4.5, 5.4) |
| 마나·경험치 지급 | 경제 시스템 | 기반은 "누가 무엇을 죽였다"만 알림 (6.1, 6.3) |
| 파괴된 시설 자리의 이동 경로 갱신 | 설치 시스템 | 기반은 "파괴됨"만 알림 (5.2, 11.1) |
| 하수인 재소환 타이머 | 소환 타워 | 기반은 "소속 하수인 사망"만 알림 (5.5) |
| 부활 위치 선택과 5초 카운트 | 플레이어(TPS) 시스템 | 기반은 다운 상태 전환과 체력 복구만 담당 (3.5) |
| 승리·패배 판정 | 상태 관리 | 기반은 "코어 파괴됨"만 알림 (2.2) |
| 피격·사망 연출의 내용 | 표현 계층 | 기반은 연출 시작 시점과 종료 대기만 담당 |
| 레벨의 위치·구역·경로 데이터 | DesertTower.Levels.Runtime | 이미 분리된 패키지, 기반은 읽지도 않음 |

원칙: **기반은 사실을 기록하고 알린다. 판단과 지급은 위 계층이 한다.**

## 2. 전투 개체 모델

### 2.1 공통 속성

전장에서 피해를 받을 수 있는 모든 것은 하나의 "전투 개체"로 등록된다. 공통 속성은 다음과 같다.

| 속성 | 설명 | 출처 |
|---|---|---|
| 식별자 | 런타임 고유 번호. 재시작 시 초기화 | — |
| 정의 참조 | 편집 가능한 데이터 자산(2.4) | 11.2 |
| 진영 | 아군 / 적군 | 3장 |
| 분류 | 캐릭터 / 시설 / 코어 | 11.1 |
| 최대 체력, 현재 체력 | 정수 또는 소수, 0 ≤ 현재 ≤ 최대 | 11.2 |
| 생존 상태 | 2.2의 상태 중 하나 | — |
| 대상 가능 여부 | 현재 공격 대상으로 선택될 수 있는가 (4장) | 4.3, 3.5 |
| 피격 지점 | 거리·시야 판정의 기준 위치. 발 위치가 아니라 몸통 높이 | 10.1 "피격 위치" |
| 공격 발생 지점 | 이 개체가 공격할 때 투사체·근접 판정이 시작되는 위치 | 10.1 "공격 발생 위치" |
| 소속 주인 | 있으면 참조. 현재는 하수인 → 소환 타워만 해당 | 5.5 |
| 파괴 가능 여부 | 항상 참. 파괴 불가능한 기본 성벽·절벽은 개체로 등록하지 않는다 | 4.1 |

### 2.2 종류별 차이

일곱 종류를 세 분류로 묶고, 분류 안에서도 다르게 처리해야 하는 것만 표시한다.

| 개체 | 분류 | 체력 0일 때 | 보상 발생 | 제거 방식 | 특이 규칙 |
|---|---|---|---|---|---|
| 일반 근접 적 | 캐릭터 | 사망 | 예 (마나+경험치) | 연출 후 제거 | — |
| 강한 근접 적 | 캐릭터 | 사망 | 예 | 연출 후 제거 | 수치만 다름, 규칙 동일 |
| 하수인 | 캐릭터 | 사망 | **아니오** | 연출 후 제거 | 소속 타워에 사망 알림. 타워 파괴 시 "소멸"(사망 아님) |
| 플레이어 | 캐릭터 | **다운** | 아니오 | **제거하지 않음** | 5초 후 최대 체력으로 부활. 다운 중 대상 불가 |
| 벽 | 시설 | 파괴 | 아니오 | 충돌·기능 즉시 제거, 잔해 연출 후 제거 | 파괴 알림 → 이동 경로 갱신 |
| 공격 타워 | 시설 | 파괴 | 아니오 | 동일 | 진행 중 투사체는 유지 (5.4) |
| 소환 타워 | 시설 | 파괴 | 아니오 | 동일 | 소속 하수인 전원 소멸 |
| 코어 | 코어 | 파괴 | 아니오 | 제거하지 않음 | 파괴 알림 → 즉시 패배 |

"사망", "파괴", "소멸", "다운"은 이름만 다른 게 아니라 **외부에 보내는 알림이 다르다**. 이 구분이 6.1의 "적 하나의 사망 보상은 한 번만", 5.5의 "타워 파괴 시 하수인은 사라진다"(보상 없음), 3.5의 "플레이어 사망은 즉시 패배가 아니다"를 동시에 만족시킨다.

### 2.3 생명주기 상태

```
[등록됨] ─ 전장 진입 ─→ [생존]
[생존] ─ 체력 0 ─→ [종료 처리 중] ─ 연출 종료 ─→ [제거됨]
[생존] ─ 체력 0 (플레이어) ─→ [다운] ─ 5초 ─→ [생존]  (체력 최대)
[생존] ─ 주인 파괴 (하수인) ─→ [소멸] ─→ [제거됨]
[모든 상태] ─ 재시작 ─→ [제거됨]
```

상태 전환 규칙:

- **생존 → 종료 처리 중**은 체력이 0이 되는 그 피해 적용에서 단 한 번만 일어난다. 이미 종료 처리 중인 개체가 추가 피해를 받으면 무시한다. 같은 프레임에 두 투사체가 동시에 적중해도 사망 알림은 한 번이다.
- **종료 처리 중**은 연출을 위한 상태다. 이 상태에 들어가는 순간 대상 가능 여부는 거짓이 되고, 시설이면 충돌체와 공격 기능도 즉시 꺼진다(5.2). 눈에 보이는 모형만 남는다.
- **다운**은 플레이어 전용이다. 개체는 등록부에 남고, 체력은 0이며, 대상 불가다. 4.3의 "사망한 플레이어를 대상으로 삼던 적은 다른 대상을 찾는다"는 대상 가능 여부가 거짓으로 바뀌는 것만으로 EnemyAI가 처리한다.
- **소멸**은 보상도 사망 연출도 없는 조용한 제거다. 하수인의 주인 파괴, 그리고 재시작 정리에 쓴다.

### 2.4 편집 가능한 데이터

기획서 11.2에서 이 기반이 담당하는 항목만 뽑는다. 종류별 정의 자산 하나에 다음을 둔다.

- 진영, 분류
- 최대 체력
- 피격 지점 오프셋, 피격 반경
- 공격 발생 지점 오프셋 (공격하는 개체만)
- 종료 연출 길이 (사망·파괴 후 제거까지의 대기 시간)
- 잔해 유지 시간 (시설만, 5.2 "짧은 연출")
- 다운 지속 시간 (플레이어만, 초기 5초)
- 부활 보호 시간 (플레이어만, 초기 0 = 없음, 3.5 "테스트 후 결정")

이동 속도·공격력·사거리·마나 보상은 이 자산에 넣지 않는다. 각각 이동, 공격, 경제 시스템의 데이터다. 레벨 패키지의 `LevelElementDefinition.gameKey`가 게임 카탈로그를 통해 이 정의 자산과 적 프리팹을 찾는 구조는 그대로 둔다.

## 3. 진영과 적대 관계

초기 버전은 두 진영이다.

| 진영 | 구성원 |
|---|---|
| 아군 | 플레이어, 하수인, 벽, 공격 타워, 소환 타워, 코어 |
| 적군 | 일반 근접 적, 강한 근접 적 |

적대 관계는 "다른 진영이면 적대, 같은 진영이면 비적대"로 시작한다. 중립은 두지 않는다.

같은 진영 사이의 피해 요청은 기반 단계에서 **거부**한다. 이것이 3.3 "아군 피해는 초기 버전에서 적용하지 않는다"의 구현 위치다. 플레이어 마력탄이 자기 벽에 맞아도 벽 체력은 줄지 않고, 투사체는 벽에 막혀 사라지기만 한다(투사체 소멸은 투사체 시스템 몫, 체력 미감소는 기반 몫).

나중에 아군 피해를 도입하려면 이 거부 규칙 하나를 데이터로 바꾸면 된다. 그래서 진영 판정은 각 공격자가 아니라 기반에 둔다.

## 4. 피해 처리

### 4.1 피해 요청의 내용

공격자는 대상의 체력을 직접 건드리지 않고 "피해 요청"을 기반에 넘긴다. 요청에는 다음이 들어간다.

| 항목 | 설명 | 누가 쓰는가 |
|---|---|---|
| 피해량 | 0 이상 | 기반 |
| 대상 | 전투 개체 식별자 | 기반 |
| 가해 개체 | 실제로 공격한 개체 (플레이어, 타워, 하수인, 적). 없을 수 있음 | 경제(6.1 "타워나 하수인이 처치해도 같은 보상"), 표현 |
| 가해 진영 | 가해 개체가 없어도 반드시 있음 | 진영 판정 |
| 피해 원인 | 기본 마력탄 / 타워 투사체 / 범위 마법 / 근접 공격 | 표현(피격 효과 선택), 통계 |
| 적중 위치·방향 | 있으면 | 표현 |

가해 개체를 요청에 실어 보내는 이유는, 사망 알림이 "누가 죽였는가"를 담아야 경제 시스템이 지급 대상을 따로 조회할 필요가 없기 때문이다. 다만 6.3의 "최종 타격 주체로 획득을 제한하지 않는다"에 따라 경제는 이 정보를 **기록용**으로만 쓰고 지급 조건으로는 쓰지 않는다.

### 4.2 적용 순서

피해 요청은 항상 같은 순서로 처리한다.

1. 대상이 등록부에 있고 생존 상태인가. 아니면 무시.
2. 가해 진영과 대상 진영이 적대 관계인가. 아니면 무시.
3. 대상이 대상 가능 상태인가. 부활 보호 중이면 무시. (초기값은 보호 없음이므로 항상 통과)
4. 현재 체력에서 피해량을 뺀다. 0 미만은 0으로 고정.
5. "피해 받음" 알림을 보낸다. 체력이 0이 되었더라도 먼저 보낸다.
6. 체력이 0이면 2.3의 종료 전환을 시작하고, 종류에 맞는 알림(사망·파괴·다운)을 **한 번** 보낸다.

3번까지의 거부는 조용히 이루어진다. 공격자에게 "실패"를 돌려주지만 오류로 취급하지 않는다. 벽 너머의 적에게 사거리 확인을 잘못해 요청이 들어와도 게임이 멈추지 않아야 한다.

### 4.3 기반이 하지 않는 검증

다음은 **요청을 보내기 전에 공격자가** 확인한다. 기반은 재확인하지 않는다.

- 사거리 안에 있는가 (4.5 "공격 판정 시 실제 사거리 안에 있는지 확인")
- 시야가 확보되는가 (5.4 "가려지면 새 대상")
- 근접 공격이 벽을 관통하지 않는가 (4.5)
- 투사체가 실제로 충돌했는가

기반이 이걸 다시 검사하면 공격 종류마다 다른 규칙을 기반이 알아야 하고, 그 순간 기반이 세 코어 시스템에 의존하게 된다. 대신 기반은 5장의 공통 질의 도구를 제공해 공격자가 같은 기준으로 검사하게 만든다.

### 4.4 회복

- **수리**(5.6): 시설 대상. 회복량을 받아 최대 체력까지 더한다. 웨이브 사이에만 가능하다는 제한과 마나 계산은 수리 UI·경제가 담당하고, 기반은 "체력을 얼마나 올릴 수 있는가(부족분)"를 알려주고 실제로 올리기만 한다.
- **부활**(3.5): 플레이어 대상. 다운 → 생존 전환과 함께 최대 체력으로 채운다.
- 자연 회복·코어 주변 회복은 6.1에 따라 없다. 회복 경로는 위 두 가지뿐이다.

## 5. 공통 질의

세 코어 시스템이 각자 다르게 구현하면 결과가 어긋나는 판정을 기반이 한 곳에서 제공한다.

### 5.1 대상 유효성

"이 개체를 지금 공격 대상으로 삼아도 되는가"에 대한 답. 참이 되려면 등록됨, 생존 상태, 요청자와 적대 진영, 대상 가능 상태를 모두 만족해야 한다.

EnemyAI의 4.3 1단계("현재 목표가 살아 있으면 유지"), 공격 타워의 5.4("죽으면 새 대상"), 하수인 교전이 모두 이 질의를 쓴다. **접근 가능성은 포함하지 않는다**. 4.2의 "이동으로 접근할 수 없는 대상을 추적하지 않는다"는 이동 시스템의 경로 질의와 조합해 EnemyAI가 판단한다.

### 5.2 거리

두 개체의 **피격 지점** 사이 거리. 발 위치 기준이 아니라는 점이 중요하다. 고저차 구간(7.2)에서 계단 위 타워와 아래 적의 거리를 발 위치로 재면 사거리 판정이 실제 시각과 어긋난다.

### 5.3 시야

한 지점(보통 요청자의 피격 지점 또는 공격 발생 지점)에서 대상의 피격 지점까지 장애물이 없는가. 장애물로 취급하는 것은 기본 지형, 기본 성벽, 플레이어가 설치한 벽과 타워다. 캐릭터(플레이어·적·하수인)는 장애물로 취급하지 않는다. 적 무리 뒤의 적도 "보인다".

이 질의 하나가 4.2 "벽 뒤나 다른 층의 대상을 거리만으로 인식하지 않는다", 5.3 "방어물이 모든 아군 사격을 자동 통과시키지 않는다", 5.4 "가려지면 새 대상"을 같은 기준으로 만든다. 시야 판정에 어떤 충돌 층을 쓰는지는 기반이 한 곳에서 정의하고, 설치 시스템은 시설을 만들 때 그 층에 넣기만 한다.

3.2의 카메라 관련 규칙("카메라 위치에서만 명중하지 않도록 발사 위치와 조준 위치를 함께 확인")도 이 시야 질의를 발사 위치 기준으로 한 번 더 호출하는 것으로 해결한다.

### 5.4 등록부 조회

- 진영별 생존 개체 목록
- 분류별 생존 개체 목록 (예: 아군 시설 전체)
- 특정 지점에서 반경 안의 적대 개체 (공격 타워의 대상 탐색, 범위 마법의 피해 대상 수집)
- 특정 개체의 소속 개체 목록 (소환 타워 → 하수인)

등록부는 "살아 있는 적이 남았는가"를 웨이브 종료 판정(2.1의 8단계)에 답하는 근거이기도 하다. 등록부에 적군 캐릭터가 0이고 출현 예정도 0이면 웨이브 종료다.

## 6. 알림과 소비자

기반은 다음 사실이 일어날 때 알림을 보낸다. 알림은 순서가 보장되고, 같은 프레임 안에서 동기적으로 전달된다.

| 알림 | 담긴 정보 | 소비자와 용도 |
|---|---|---|
| 체력 변경 | 개체, 이전·현재 체력 | HUD(플레이어·코어·조준한 시설 체력), 시설 손상 표현(재질 변화) |
| 피해 받음 | 개체, 피해 요청 전체 | 피격 연출·음향, 코어 피격 경고 방향(7.3), EnemyAI의 "공격받음" 인지(4.3 보완 규칙 — 무한 추적 금지의 판단 재료) |
| 사망 | 적 개체, 가해 개체, 가해 진영 | **경제**(마나·경험치 지급, 1회), 웨이브 진행(남은 적 수), EnemyAI·타워(대상 재선택) |
| 파괴 | 시설 개체, 가해 개체 | **설치 시스템**(점유 해제, 이동 경로 갱신), 소환 타워(소속 하수인 소멸 지시), HUD 경고, EnemyAI(막힌 길 재확인 → 이동 재개) |
| 코어 파괴 | 코어 | **상태 관리**(즉시 패배) |
| 다운 | 플레이어 | TPS(조작 잠금, 부활 카운트 시작), EnemyAI(대상 재선택), HUD |
| 부활 | 플레이어, 위치 | TPS(조작 복구), 카메라 |
| 소멸 | 개체 | 소환 타워(하수인 수 갱신, 재소환 여부 판단), 표현(조용한 제거) |
| 제거 완료 | 개체 | 오브젝트 풀 반환 |

설계 규칙:

- 소비자는 알림을 받고 자기 일을 하지, 기반에 무언가를 돌려주지 않는다. 기반은 소비자가 몇 명인지 모른다.
- **사망 알림은 개체당 평생 한 번**이다. 이것이 6.1의 중복 지급 방지를 기반 수준에서 보장하는 장치다. 경제 시스템이 별도로 "이미 지급했는가"를 기억할 필요가 없다.
- 하수인 사망은 "사망" 알림을 쓰지만, 경제는 가해·피해 진영을 보고 아군 사망에는 지급하지 않는다. 즉 경제의 지급 조건은 "적군 캐릭터의 사망"이다.
- 파괴 알림 순서: 충돌·기능 제거 → 파괴 알림 → 잔해 연출 시작. 알림을 받은 설치 시스템이 경로를 갱신하는 시점에 이미 충돌체가 없어야 13.1의 "시설 파괴 직후 적이 이동을 재개하는가"가 성립한다.

## 7. 재시작 정리

6.3 "스테이지 재시작 시 레벨, 마나, 해금, 시설 상태를 초기화한다"와 13.1 "재시작 시 이전 시설·적·성장 상태가 남지 않는가"의 절반은 기반이 담당한다.

재시작 요청이 오면 기반은 등록부의 모든 개체를 **소멸** 처리한다. 사망·파괴 알림이 아니라 소멸이므로 보상도, 경로 갱신 요청도, 패배 판정도 일어나지 않는다. 그 다음 등록부를 비우고 식별자 카운터를 초기화한다.

코어와 플레이어처럼 "제거하지 않는" 개체도 등록부에서는 제거된다. 새 스테이지가 시작되면 다시 등록한다. 즉 재시작 후 살아남는 상태는 없다.

정리 순서는 소속 관계를 따른다. 주인(소환 타워)보다 소속(하수인)을 먼저 소멸시켜, 정리 도중 "주인 파괴 → 하수인 소멸" 규칙이 중복 실행되지 않게 한다.

## 8. 다른 시스템과의 계약

### 8.1 TPS 코어

- 플레이어를 아군 캐릭터로 등록한다.
- 기본 마력탄·화염구가 적중하면 피해 요청을 보낸다. 가해 개체는 플레이어, 원인은 각각 기본 마력탄·범위 마법.
- 범위 마법은 5.4의 반경 조회로 대상을 모으고, 대상마다 피해 요청을 하나씩 보낸다. 기반은 "범위 피해"라는 별도 개념을 갖지 않는다.
- 다운 알림을 받으면 조작을 잠그고 5초 후 부활을 요청한다. 부활 위치 선택은 TPS가 한다.
- 발사 전 3.2의 이중 확인에 5.3 시야 질의를 쓴다.

### 8.2 타워 디펜스 코어

- 설치 확정 시 시설을 아군 시설로 등록하고, 등록이 끝난 뒤에만 마나를 차감한다(5.1 "성공했을 때만 차감").
- 공격 타워는 5.4 반경 조회 + 5.1 유효성 + 5.3 시야로 대상을 고르고, 투사체 적중 시 피해 요청을 보낸다. 가해 개체는 타워.
- 소환 타워는 하수인을 소속 주인 = 자기 자신으로 등록한다. 하수인 사망 알림을 받으면 8초 재소환을 시작한다. 자기 파괴 알림은 받을 필요 없다. 기반이 소속 개체를 소멸시킨다.
- 파괴 알림을 받으면 점유를 해제하고 이동 경로를 갱신한다.
- 수리 UI는 기반에서 부족 체력을 읽어 비용을 계산하고, 결제 후 회복을 요청한다.
- 철거는 소멸 요청이다. 파괴가 아니므로 파괴 알림·잔해 연출이 없고, 환급은 경제가 계산한다.

### 8.3 EnemyAI

- 적은 생성기가 적군 캐릭터로 등록한다.
- 4.3 목표 선택의 모든 단계에서 5.1 유효성으로 후보를 거른다. 접근 가능성은 이동 시스템에 묻는다.
- 4.2 인식은 5.2 거리(10m) + 5.3 시야로 한다.
- 근접 공격 판정 시 5.2 거리와 5.3 시야를 다시 확인하고("벽 너머 관통 금지") 피해 요청을 보낸다. 가해 개체는 적, 원인은 근접.
- 대상의 사망·파괴·다운 알림 중 자기 목표에 해당하는 것을 받으면 4.3을 다시 돈다.
- 4.3 2단계 "진행을 막는 파괴 가능한 시설"은 등록부에서 아군 시설만 걸러 찾는다. 기본 성벽은 등록돼 있지 않으므로 자연히 후보에서 빠진다(4.1).

### 8.4 경제·상태 관리·HUD

- 경제: 적군 캐릭터의 사망 알림 하나당 마나·경험치를 한 번 지급한다. 가해 개체는 무시하고 기록만 한다.
- 상태 관리: 코어 파괴 알림 → 패배. 등록부의 적군 캐릭터 0 + 출현 예정 0 → 웨이브 종료. 재시작 → 7장 정리 요청.
- HUD: 체력 변경·피해 받음·파괴 알림으로 표시와 경고 방향을 갱신한다.

## 9. 어셈블리 위치

레벨 패키지의 원칙("Runtime 데이터는 Input System, NavMesh, UnityEditor를 참조하지 않는다")을 그대로 따른다.

```
DesertTower.Combat.Runtime      ← 이 문서의 시스템
  └─ Unity 기본 타입만. Levels.Runtime도 참조하지 않음.

DesertTower.Levels.Runtime      ← 기존. Combat을 모름.

게임 코어 (TPS / TD / EnemyAI)
  ├─ DesertTower.Combat.Runtime
  ├─ DesertTower.Levels.Runtime
  └─ AI Navigation, Input System 등
```

기반이 레벨 패키지를 참조하지 않는 이유는, 레벨은 "공간"이고 기반은 "상태"라서 서로 알 필요가 없기 때문이다. 둘을 잇는 것은 생성기와 설치 시스템이다. 기반이 NavMesh를 모르기 때문에 5.3 시야 질의는 물리 충돌만 쓴다.

기반은 EditMode 테스트가 가능해야 한다. 피해 순서, 사망 1회 보장, 진영 거부, 소속 소멸 순서, 재시작 정리는 씬 없이 검증할 수 있게 설계한다.

## 10. 검증 기준

기획서 13.1을 기반 관점으로 옮긴다. 각 항목은 자동 테스트 또는 진단 로그로 확인한다.

| 기획서 13.1 | 기반이 보장할 것 | 확인 방법 |
|---|---|---|
| 시설 파괴 직후 적이 이동을 재개하는가 | 파괴 알림 전에 충돌체가 이미 제거됨 | 파괴 알림 수신 시점에 시설 충돌 질의가 거짓인지 테스트 |
| 타워 파괴 시 소속 하수인과 상태가 정리되는가 | 주인 파괴 → 소속 전원 소멸, 사망 알림 아님 | 하수인 2명 등록 후 타워 파괴 → 소멸 알림 2회, 사망 알림 0회 |
| 모든 처치 주체가 동일하게 보상하는가 | 가해 개체와 무관하게 사망 알림 형식이 동일 | 플레이어·타워·하수인 각각이 처치 → 알림 내용 비교 |
| 재시작 시 이전 상태가 남지 않는가 | 정리 후 등록부 0, 알림 없음 | 재시작 후 등록부 크기와 보상 알림 횟수 검사 |
| (6.1) 사망 보상은 한 번만 | 같은 프레임 다중 피해에도 사망 알림 1회 | 체력 1인 적에게 피해 3건 동시 적용 → 알림 1회 |
| (3.3) 아군 피해 없음 | 같은 진영 요청 거부 | 플레이어 → 벽 피해 요청 → 체력 불변 |
| (3.5) 플레이어 사망은 패배 아님 | 다운 전환, 등록부 유지, 패배 알림 없음 | 플레이어 체력 0 → 다운 알림 1회, 코어 파괴 알림 0회 |
| (4.2) 벽 뒤 대상 인식 금지 | 시야 질의가 설치 벽을 장애물로 판정 | 벽을 사이에 둔 두 개체 → 시야 거짓 |

## 11. 남은 결정

프로토타입을 보며 정할 것:

- 체력을 정수로 할지 소수로 할지. 수리 비용을 "회복 비율"로 계산하므로(5.6) 소수가 편하지만, HUD 표시와 밸런스 표는 정수가 읽기 쉽다. 초기 권장: 내부 소수, 표시 정수 올림.
- 부활 보호 시간을 대상 불가로 구현할지, 피해 요청 거부로 구현할지. 전자는 적이 아예 무시하고, 후자는 적이 때리지만 안 닳는다. 3.5의 의도("반복 사망 방지")는 전자에 가깝다.
- 종료 처리 중인 시설의 잔해가 시야를 가리는가. 5.2 "길을 막지 않는다"는 이동 이야기이고 시야는 언급이 없다. 초기 권장: 가리지 않음(충돌 제거와 함께 시야 층에서도 제외).
- 원거리 적·방패병 도입 시(4.6 추후) 피해 원인 종류와 방향 정보의 확장. 지금은 필드만 비워두고 규칙은 넣지 않는다.
- 피해 받음 알림을 EnemyAI가 "공격받음" 판단에 쓸지 여부. 4.3 보완 규칙은 "공격받았다는 이유만으로 추적하지 않는다"이므로, 알림은 보내되 EnemyAI가 무시하는 것으로 시작한다.
