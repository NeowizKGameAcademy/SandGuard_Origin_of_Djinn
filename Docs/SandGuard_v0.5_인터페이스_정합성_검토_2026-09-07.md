# SandGuard v0.5 기획서와 기존 인터페이스 정합성 검토

검토일: 2026-09-07

기준: [최신 PPTX](E:/AI/Projects/DesertTower/Docs/SandGuard_Origin_of_Djinn_게임기획서_v0.5_SkillTree_UI_Boss.pptx), Assets/Interfaces의 34개 계약, Assets/Gameplay/Contracts, Assets/Combat, 레벨 데이터 및 기존 설계 문서.

슬라이드는 파일에 저장된 실제 순서로 표기한다. 9·10번째 슬라이드는 화면에 인쇄된 페이지 숫자가 서로 뒤바뀌어 있다.

**판정: 공통 기반은 재사용 가능하지만, v0.5에 바로 맞는 상태는 아니다.** 피해·생명·마나 예약·읽기/명령 분리는 유지할 수 있다. 코어 도달 규칙, 지정 슬롯 건설, 선택형 성장, 이동 능력과 보스 상태는 변경 또는 보완이 필요하다.

현재 Gameplay/Runtime의 구현은 PriorityTargetPolicy와 CompositePlacementValidator 두 개의 순수 정책/검사 조합이다. 실제 ManaWallet, FacilityBuilder, 플레이어 전투·보스·게임 HUD 구현과 혼동하면 안 된다. 레벨 진단용 이동/웨이브는 별도 도구다. [현 구현 범위](E:/AI/Projects/DesertTower/Docs/Desert_Tower_인터페이스_개선_반영_v0.4.md:14)

**1. 코어 도달 처리: 기존 설계와 직접 충돌 — 최우선**

PPTX 10·11·13장은 도착한 적을 즉시 흡수하고 안정도를 일반 10, 정예 20, 자히르 50만큼 줄인다. 변경 전 [방어장치 설계(현재는 후속 결정 반영)](E:/AI/Projects/DesertTower/Docs/Desert_Tower_방어장치_설계_v0.1.md:112)은 접촉 즉시 피해를 명시적으로 금지하고 코어 공격도 MeleeHit를 거치게 한다. 이 지침을 유지하면 새 핵심 루프가 구현되지 않는다.

권장 변경: 검증된 코어 도달 처리 서비스에서 적 ID별로 도달을 한 번만 확정하고 안정도 감소·적 제거·웨이브 집계를 함께 반영한다. 수치 저장과 피해 적용은 기존 IHealth/IDamageable을 재사용할 수 있다. 도달을 근접 공격 성공이나 일반 처치와 같은 사건으로 처리하지 않는다.

기존 IDespawnable과 [IWaveStateReader](E:/AI/Projects/DesertTower/Assets/Interfaces/IWaveStateReader.cs:9)의 Died/Despawned 중복 집계 방지는 활용할 수 있다. 흡수 적의 처치 경험치 지급 여부는 PPTX에 명시되어 있지 않으므로 결정 사항으로 남긴다. 마지막 적 흡수로 코어가 0이 되는 경우에는 적 수가 0이라는 이유로 승리가 먼저 확정되지 않도록 해야 한다.

**2. 지정 슬롯 8개: 현재 요청·점유 모델은 자유 격자 배치 중심 — 최우선**

PPTX 8·10·15장은 빈 지정 슬롯에 시설을 선택해 건설하며 자유 배치를 제외한다. 현재 [PlacementRequest](E:/AI/Projects/DesertTower/Assets/Gameplay/Contracts/PlacementContracts.cs:9)는 FacilityId·Position·Rotation이고, [IFacility](E:/AI/Projects/DesertTower/Assets/Interfaces/IFacility.cs:24)는 월드 격자 OccupiedCells를 노출한다. [LevelMarker](E:/AI/Projects/DesertTower/Assets/DesertTowerLevelEditor/Runtime/LevelMarker.cs:7)와 LevelLayout에는 전용 건설 슬롯 데이터가 없다.

권장 변경: SlotId를 기준으로 건설을 요청하고 슬롯 데이터가 위치·회전·허용 시설을 결정하게 한다. 슬롯의 비어 있음/점유/사용 가능 상태와 변경 통지를 제공한다. 레벨 저작·저장·불러오기·검증에도 슬롯을 반영한다. 슬롯 수 8은 이 스테이지의 데이터·검증 조건으로 두고 범용 인터페이스에 상수로 넣지 않는다.

현재 Vector2Int 점유를 여러 층의 유일한 점유 키로 그대로 쓰면 같은 XZ의 상·하층 슬롯을 구분하지 못한다. 지정 슬롯 ID를 점유 기준으로 삼는 편이 새 기획에 맞다. 격자는 필요한 경우 충돌 검사 내부 도구로 남길 수 있다. IPlayerInput.SlotSelected는 기존 문서상 핫바 번호이므로 건설 지점 ID와 구별해야 한다.

마나 예약과 전체 작업 확정이라는 IFacilityBuilder 원칙은 유지한다. 자유 배치 회전·완전 차단 기능은 새 MVP에서의 필요성을 다시 판단하되, 기존 차단 계약을 자동으로 삭제할 근거는 없다.

**3. 마나 공급과 기본 공격: 지갑 계약은 맞지만 사용하는 규칙이 달라짐 — 최우선**

PPTX 4·13장은 코어 복귀 충전과 기본 마법 비용 5를 명시한다. 기존 [PlayerBasicAttack 설계](E:/AI/Projects/DesertTower/Docs/Desert_Tower_컴포넌트_목록_v0.1.md:83)는 마나 소비 없음이고, [KillRewardDispenser 설계](E:/AI/Projects/DesertTower/Docs/Desert_Tower_컴포넌트_목록_v0.1.md:183)는 처치 시 마나와 경험치를 지급한다.

권장 변경: 기본 공격도 실제 발사와 마나 소비를 함께 확정하고, 코어 충전 서비스에서 범위·시작/중단·충전량을 관리한다. 기존 Gain과 Changed는 사용할 수 있다. 초당 충전량을 정수 마나로 지급할 때 프레임마다 소수 부분을 버리지 않도록 누적량을 관리한다. 최대 마나 증가도 지갑 소유 서비스에서 적용하고 UI에 통지한다.

v0.5는 처치 경험치를 명시하지만 처치 마나를 별도로 확정하지 않는다. 기존 처치 마나를 그대로 가져오면 코어 복귀 판단을 약화시킬 수 있다. 존치 여부와 충전 중 행동 제한은 기획에서 확정해야 한다.

**4. 시설 강화와 철거: 강화 계약 누락, 환급 산식 불일치**

PPTX 8·9·13장은 시설별 1회 강화, 강화비는 건설비의 60%, 철거 환급은 건설비의 50%다. 현재 [IFacilityMaintenance](E:/AI/Projects/DesertTower/Assets/Interfaces/IFacilityMaintenance.cs:4)에는 수리/철거 견적과 실행만 있다. IFacility에도 강화 여부나 단계가 없다.

권장 변경: 강화 견적·실행과 강화 상태 조회를 추가한다. 1회 제한, 해금 조건, 비용, 효과를 같은 작업으로 확정한다. 메서드는 기존 Maintenance를 확장하거나 별도 서비스로 나눌 수 있으며 지금 모든 시설에 새 인터페이스를 일괄 추가할 필요는 없다.

기존 [철거 산식](E:/AI/Projects/DesertTower/Docs/Desert_Tower_인터페이스_구현_v0.2.md:66)은 건설비 × 현재 체력 비율 × 50%의 내림이다. 예를 들어 건설비 40, 체력 50%이면 기존은 10, 새 PPTX 문구를 그대로 적용하면 20이다. 새 문구에는 체력 비례가 없으므로 통일이 필요하다. 비용 55의 절반 27.5를 정수 마나로 처리하는 반올림 규칙과 강화비의 환급 포함 여부도 명시해야 한다.

새 PPTX가 수리 삭제 또는 전투 중 강화·철거 허용을 명시한 것은 아니다. 기존 준비 단계 제한과 수리 기능은 유지 여부를 확인할 항목이다.

**5. 선택형 스킬트리: 읽기 계약만으로는 선택·포인트 소비를 표현할 수 없음**

PPTX 6장은 기초/기동·공격 마법·시설 해금의 분기와 한정된 포인트를 요구한다. [IProgressionReader](E:/AI/Projects/DesertTower/Assets/Interfaces/IProgressionReader.cs:4)는 레벨/경험치만, [IUnlockQuery](E:/AI/Projects/DesertTower/Assets/Interfaces/IUnlockQuery.cs:4)는 최종 해금 여부만 제공한다. 기존 설계는 레벨업에 따른 자동 해금이다.

권장 변경: 스킬 노드 정의, 선행 조건, 비용, 습득 상태, 남은 포인트의 조회와 TryLearn(nodeId) 같은 명령 경계를 추가한다. 포인트 부족·선행 미충족·중복 습득 시 상태가 바뀌지 않아야 한다. 습득 결과로 기존 IUnlockQuery와 능력치/마법 정의에 효과를 전달한다. 초기화는 15장의 제외 범위에 있으므로 MVP API에 넣지 않는다.

스킬트리 이미지는 노드 연결을 보여주는 콘셉트이며 실제 노드명·개별 비용·효과 수치가 들어 있지 않다. 이미지의 모든 연결을 확정 데이터로 간주해서는 안 된다. MaxLevel은 이미 속성이므로 6/10의 수치 변경 자체는 인터페이스 재설계 사유가 아니다.

**6. 대시·더블 점프: 플레이어 입력과 사용 가능 상태 계약 보완 필요**

PPTX 5장은 대시 10마나/4초 쿨다운, 공중 추가 점프 1회를 요구한다. [IPlayerInput](E:/AI/Projects/DesertTower/Assets/Interfaces/IPlayerInput.cs:5)에는 점프·대시 의도가 없다. InputSystem_Actions 자산에는 Jump/Interact/Sprint가 있지만 이를 전달하는 현재 게임플레이 계약은 빠져 있다. [DiagnosticWalkthrough](E:/AI/Projects/DesertTower/Assets/DesertTowerLevelDiagnostics/Runtime/DiagnosticWalkthrough.cs:20)는 진단용 보행/달리기이며 이 기능의 구현이 아니다.

권장 변경: 점프·대시 의도를 노출하고 플레이어 이동 컴포넌트가 지상 여부, 공중 추가 점프 잔여 횟수, 잠금·사용 가능 상태를 관리하게 한다. ISpellStateReader의 비용/쿨다운 구조는 재사용 가능하지만 SpellState만으로 착지 시 추가 점프 복구를 표현하지 못한다.

IMovementController는 주석상 적·하수인의 목적지 이동용이므로 플레이어 점프 기능을 여기에 섞지 않는다. 기존 절벽 PlayerBlocker 설계도 정상적인 점프 지름길을 막지 않는지 레벨 검증이 필요하다. 더블 점프 비용과 대시의 공중 사용·방향 규칙은 PPTX에서 미정이다.

**7. 보스와 HUD: 공통 체력은 충분하지만 패턴·시설 정지·층별 정보는 추가 필요**

PPTX 12장의 자히르는 체력 1,200, 정면 타워 피해 50% 감소, 주변 시설 5초 정지, 체력 35% 이하 경로 한 구간 생략을 요구한다.

- 방패: [DamageInfo](E:/AI/Projects/DesertTower/Assets/Combat/DamageInfo.cs:7)에 CauseId와 HitDirection이 있어 수신부 피해 정책을 확장할 수 있다. 다만 방향 벡터 기준과 타워/플레이어 피해 구분은 아직 계약화되지 않았다. 발사 후 타워가 제거되어도 피해 출처를 판단할 수 있도록 CauseId 카탈로그나 요청에 담는 출처 정보의 규칙이 필요하다. IDamageable 자체를 전면 변경할 필요는 없다.
- 시설 정지: IFacility에는 가동 여부나 정지 잔여 시간이 없다. 정지 적용과 상태 조회를 제공하고 타워 공격·소환 타이머·HUD가 이를 사용하게 한다. 이미 나온 소환수까지 정지되는지, 중첩 폭탄이 시간을 갱신하는지는 미정이다.
- 갈고리 상승: 일반 IMovementController는 경로 진행 구간이나 보스 패턴을 모른다. 보스 전용 동작이 사용할 출발/도착 구간 또는 링크를 레벨 데이터와 연결한다. 일반 고립 복구를 보스의 의도된 구간 생략으로 재해석하지 않는다.

PPTX 7장의 HUD는 아래처럼 대응된다. 내장 콘셉트 이미지도 본문에 적힌 배치를 따르고 있다. 다만 실제 게임 HUD 구현은 아직 없어 픽셀 배치의 일치 여부를 판정한 것은 아니다.

| 우측 하층·중층·상층 위험 | 공간 조회와 LevelArea의 높이 범위 | 층 식별, 적 소속 층 집계, 위험도 표시 기준과 변경 통지 |
| 좌하단 체력·경험치·레벨 | IHealth, IProgressionReader | 뷰 연결 |
| 우하단 램프 마나·능력 | IManaReader, ISpellStateReader | 대시·추가 점프 상태 연결 |
| 건설/강화 상호작용 | 건설 명령과 기존 견적 구조 | 선택 슬롯 상태, 허용 시설, 강화 가능 여부와 안내 |

IWaveStateReader의 전체 남은 적 수와 NextRouteIds는 층별 위험도를 대신할 수 없다. 별도 집계 뷰 모델을 두고 HUD가 매 프레임 전장을 직접 검색하지 않게 하는 것이 기존 읽기/명령 분리 방향과 맞다.

**기획서에서 먼저 통일할 사항**

| 항목 | 기획서 근거 | 결정할 내용 |
|---|---|---|
| 최대 레벨 | 4·6장 Lv.10, 13장 Lv.6. 4장 노트도 Lv.6 | 단일 상한과 경험치 표 |
| 포인트 10개 | 6장 | Lv.1 시작 후 레벨업마다 1개라면 Lv.10까지 9회. 초기 지급 등 총 10개 획득 방식 명시 |
| 마나 충전 | 4장 약 2초, 13장 20/초 | 2초가 완충인지 상호작용 대기인지 명시. 빈 100마나를 20/초로 채우면 5초, 125면 6.25초 |
| 시설 범위 | 6장 모래시계 오벨리스크, 9·15장 MVP 3종 | 오벨리스크가 MVP 포함인지 후속 노드인지 결정 |
| 적 범위 | 11장 일반·빠른·방패/철거꾼, 15장 적 3종 | 방패/철거꾼이 한 종류인지 별도 종류인지 확정 |
| 강화·철거 | 8·13장 | 강화 효과, 정수 비용 처리, 환급 기준, 허용 페이즈 명시 |
| 미정 동작 | 4·5·10·12장 | 충전 중 행동, 더블 점프 비용, 흡수 보상, 정지된 소환 타워의 소환수 처리 |

위 미정 사항은 검토자의 임의 결정으로 코드에 반영하지 않았다. 보스 수치와 일정, HUD 이미지 수치는 발표자 노트상 프로토타입 가설/예시이므로 인터페이스 상수로 고정하지 않는 편이 적절하다.

**권장 반영 순서**

1. 코어 도달·마나 순환·지정 슬롯 건설을 새 핵심 루프 기준으로 먼저 맞춘다. 관련 기존 문서의 반대 지침을 함께 갱신한다.
2. 이동 능력, 스킬 선택, 1회 강화와 환급 계약을 보완한다. 기존 피해·지갑·조회 계약은 재사용한다.
3. 보스 패턴과 시설 정지, 층별 위험도 집계를 연결하고 새 HUD를 구성한다.
4. 구현 후 코어 도달 중복/마지막 적 패배, 같은 슬롯 이중 건설/층간 점유, 마나 부족 시 공격·대시 실패, 두 번째 강화 거부, 선행 스킬 미충족, 착지 시 점프 복구, 보스 방향 피해와 정지 종료를 통합 검증한다.

기존 문서에 기록된 32개 EditMode 테스트 통과는 당시 계약의 검증 결과다. 새 v0.5 요구사항의 구현·검증 완료를 의미하지 않는다. 이번 검토에서는 코드 변경이 없어 테스트를 새로 실행하지 않았다.
